# dsh-cabinet v0.2.3 设计方案（组阁确认停等点）

> **已并入 v0.2.4（docs/设计方案-v0.2.4.md），本稿废止，留作历史对照。**
> 组阁确认机制的最终形态以 v0.2.4 §一 为准（确认卡增预答摘要行，
> 其余内容原样迁移）。

> 基线：v0.2.2（已实建，verify 51 项 + smoke 54 项全绿）
> 新增机制：**组阁前确认停等**——任务受理后、R1 派发前，主持人把组阁方案
> （席位→阁员→模型路由→思考强度）呈现给用户，用户可改定，显式确认后才
> 派发第一席。

## 一、动机

现状的披露时序是错位的：钉扎 vs 实际的"开场披露"与 R1 立场书**同时**
呈现（速览阶段），用户看到失配时 4–6 席的 token 已经烧掉。10-09 首场
锋撞同源、靠主持人临场改钉救火——如果当次改钉不合用户意，纠正成本是
整场重来。把披露**前移并赋予行动权**，成本为零（停等不消耗委派额度），
换来的是组阁错误的免费拦截点。

## 二、机制设计

### 2.1 流程插入点

```
现状：第 0 步前置检查（组阁+三维检查+路由核对）→ 第 1 步 R1 派发 → 第 2 步停等
新版：第 0 步前置检查 → 第 0.5 步【组阁确认停等】→ 第 1 步 R1 派发 → …
```

第 0.5 步是**强制停等点**，优先级与"R1 后必停"同级：未获用户显式确认
不得派发任何席位。

### 2.2 组阁确认卡（呈现内容）

组阁完成（含三维不重合检查、路由核对）后，向用户输出一张确认卡：

```
## 组阁确认（未派发任何席位，calls 0/N）

议题：… ｜ 档位：standard（4席×1轮）｜ 续谈模式：关

| 席位 | 阁员 | provider | model | 思考强度 | 钉扎=实际？ |
|------|------|----------|-------|---------|------------|
| 红队批判官 | 锋 | kimi-coding | k3 | high | 一致 |
| 架构官 | 远 | kimi-coding | k3 | high | 一致 |
| 工程官 | 谋 | zai-coding-cn | glm-5.3-flash | 继承默认 | 一致 |
| 成本官 | 众 | deepseek-account | deepseek-flash | max | 一致 |

三维检查：气质 4 异 / 立场 4 异 / 模型 3 家族；红队异源 ✓（vs 会话 glm-5.3）
失配披露：（无 / 逐席列出并注明已写入该席简报）

可回复：
- "组阁确认" / "开议" —— 按上表派发
- "锋换成 zai-coding-cn/glm-5.3 high" —— 改定某席（可多条）
- "免确认直接开" —— 跳过本停等点（仅本场）
- "散会" —— 终止
```

### 2.3 用户改定的处理规程

1. 改定逐条落回组阁表后**重跑完整检查**：list_subagent_models 路由核对 +
   三维不重合检查（含红队异源失败关闭），任一不过 → 不出新确认卡，
   直接说明哪条不合规。
2. **红队铁律与用户主权冲突时**：用户改定导致红队与会话同源的，主持人
   响亮提示风险并要求二次确认；用户坚持则放行，disclosure 大写标注
   "红队同源系用户显式覆盖铁律"——铁律的默认值是机制给的，最终裁量权
   在用户，但覆盖必须留痕。
3. 改定确认后**重新输出确认卡**（改定后状态），再等一次确认——改定
   不直接触发派发，防"手滑改错即烧 token"。
4. events.jsonl 记录：组阁呈现（setup）、用户改定内容（steering）、
   确认动作（steering）；用户否决掉的红队违规改定计入 index 的
   gate_blocks。

### 2.4 与既有机制的交互

| 既有机制 | 交互 |
|---|---|
| R1 后必停 | 不变——两个停等点串联：组阁确认（0 成本）在 R1 前，速览停等在 R1 后 |
| 红队铁律三修（P3） | 不变；新增 §2.3-2 的"用户显式覆盖"通道（此前铁律无出口，用户想同源只能去改 config） |
| 续谈形态（CONTINUATION_ENABLED） | 正交——确认卡照常标注续谈模式；两形态共用本停等点 |
| 预算 | 零影响：确认停等在首次派发前，calls 恒为 0；用户改定不产生委派 |
| 升档 | 升档重调 start 后组阁变化（席位增加）→ **新场重新过组阁确认**（与"升档即冷启动"同源：新计划不继承旧场任何运行态） |
| 三维检查 | 从"组阁后必做"变为"组阁确认卡的前置条件"——检查不过则不出卡、直接报错 |
| 评分卡 | 不变（仍决定开不开阁、开哪档） |

### 2.5 免确认通道的边界

"免确认直接开"仅当场有效、须用户显式说出，不设 config 级默认——否则
本机制退化为可被遗忘的默认值。快速通道给熟手，默认值保护所有人。

## 四、故障与边界

| 情形 | 处置 |
|---|---|
| 用户不回复 | 停等即终态，不烧 token；会话自然搁置 |
| 用户改定的路由不存在 | 路由核对 FAIL，说明并留在确认环节，不派发 |
| 用户改定致三维检查不过 | 说明哪维、给修复建议，留在确认环节 |
| 用户改定致红队同源 | §2.3-2：响亮提示→二次确认→放行留痕 |
| 免确认后用户中途想改模型 | 走既有轮间介入（点名/散会），或散会后改 config 重开 |

## 五、验收

- 计划文本渲染目检：确认卡在 R1 派发步骤之前；两形态（continuation
  开/关）各渲一次。
- 首场实跑核对：确认卡呈现→用户改定一席→重检→再确认→派发；
  events 有组阁呈现/改定/确认三条；改定生效于实际派发路由。
- 发布门新增机检全绿。
