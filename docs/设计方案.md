## 一、原插件分析（cabinet 0.3.0）

### 1.1 安装包构成

| 件 | 性质 | 内容 |
|---|---|---|
| `cabinet-plugin-0.3.0.zip` | 插件本体（14 文件） | `manifest.json`、`main.js`、4 个技能 md、`config/tiers.json`、`schemas/protocol-v2.json`、面板 `views/models.html`、发布门 `verify.mjs`/`smoke.mjs` |
| `ministers/` | **宿主侧资产，不随插件安装** | 8 个阁员子智能体定义（锋/据/立/谋/远/众/审/骨）+ README + 构建日志 |
| `verification-bundle-0.3.0.json` | 完整性锚 | main.js SHA-256、发布门 84 项检查记录 |

### 1.2 核心功能

cabinet 是**低频重决策的多角色议事编排器**，设计哲学是"插件只产出计划文本，执行全靠宿主父智能体自律"（M1′ 阶段约束：main.js 无 I/O、无状态）。

- **开阁工具 `start`**：输入议题/场景/档位/目标，返回自包含的议事编排计划（席位、轮次、预算硬顶、中止点、灾备表）。
- **三档预算双轨制**（`config/tiers.json` 唯一真源）：standard=4 席×1 轮（硬顶 9 次委派）、advanced=5×2（16 次）、max=6×2（19 次）。调用轨执法、token 轨软参考。
- **三场景角色包**：coding（架构官/工程官/成本官）、writing（立意官/结构官/读者代理/事实核查官）、research 通用默认（正方/反方/方法审查官/信源核查官），外加固定席红队批判官。
- **专职阁员两级映射**：8 个阁员子智能体（钉扎不同 provider 家族模型）→ 席位优先映射专职席，缺席走能力征召；**三维不重合检查**（气质×立场×模型，`checkSeatDimensions` 纯函数）+ 红队异源铁律。
- **议定书 protocol.json schema v2**：分歧不空才能合议、证据三级标注（核验/推断/转述）、cites 缺失不静默接受、degraded 标记、成本决算（calls/deviation/reassigns）。
- **归档**：`.cabinet/<时间戳>-<slug>/` 下 round-N.jsonl、protocol.json、events.jsonl（10 值 phase 规范）、index.jsonl。
- **阁员模型面板（0.3.0 新增）**：`views/models.html` + `onPanelInvoke` 五通道（state/authorize/save/export/audit）。

### 1.3 配置项与依赖

- `manifest.json`：6 项权限（`agent.prompt.inject`/`agent.tool.register`/`ui.view`/`models.list`/`fs.read`/`fs.write`），fs 限定 userSelected root + `cabinet-*.md` scope；`engines.piDesktop >= 0.16.0`。
- 宿主 API：`pi.agent.registerTool`、`pi.fs.*`、`pi.models.list`、`pi.session.getLlmContext`、`pi.plugin.getSettings/getDataPath`、`panel.invoke`。
- 阁员依赖 PI 特有机制：全局子智能体目录 `%USERPROFILE%\.agents\subagents\`，frontmatter `model:`/`thinkingLevel:` 钉扎。
- 外部环境：至少两家模型 provider（混编需要）。

## 二、dsh 侧关键发现（决定移植形态）

经解包 `app.asar`（约 150 个 `@deepseek-ai/dsh-*` cordis 插件包）调研确认：

1. **dsh 插件 = cordis bundle（npm 包）**：`package.json` 声明 `dsh.bundle.patch` → patch 按序叠加（bundles → profile `cordis.patch.yml` → `--patch`）→ 入口导出 `{ name, inject, Config?, apply(ctx, config) }`（ESM）。安装 = profile 目录加依赖 + `dsh.profile.bundles` 登记。版本闸：`evaluatePluginCompatibility` 只查 `@deepseek-ai/dsh*` peerDependencies——**不声明即无约束**。
2. **dsh 不消费 `~/.agents/subagents/*.md`**：全 asar 无解析者。PI 侧已装的 8 个阁员文件在 dsh **不生效**。dsh 的子智能体是**运行时委托**：`subagent`（spawn，continuable）/`subagent_fork`/`send_message`/`interrupt_agent`/`list_agents`，provider/model/reasoning_effort 由委派参数指定。`thinkingLevel` 的对应物是 `reasoningEffort`（off/low/high/max）。（v0.1.2 修正：standard preset 工具面无 `wait_agent`——它仅存在于实验性 agent-team 包，asar 源码核验，2026-10-11）
3. **无权限清单沙箱**：插件 host 代码以 harness 进程身份执行，进程内全权限；沙箱只作用于 agent 工具调用层。
4. **模型事实**：内置三条 DeepSeek 相关路由——`deepseek-official`（`DEEPSEEK_API_KEY`）与 `deepseek-account`（应用内登录账号），默认目录 `deepseek-flash`（文本+图像）/ `deepseek-v4-pro`（纯文本）。加上用户 patch 里的 `zai-coding-cn`（GLM）与 `kimi-coding`（Kimi），**三家齐备，原家族分配表可原样落地**。
5. **工具注册可绕过 defineTool**：`ctx.tools.register()` 接受手写 JSON Schema 的原生定义对象，从而**不需要 import 任何 `@deepseek-ai/*` 包**——规避"安装内包与 npm 登记处版本漂移"的双重解析风险（npm 上 `@deepseek-ai/dsh-tools` 仅 0.0.1-rc.1，远落后于安装内 0.2.0-rc.2）。
6. **UI 扩展**需 client bundle（预构建 `lib/client.js`）+ slots 注册——本方案不采用（见 §三决策）。

## 三、复用 dsh 自带能力的评估

| dsh 自带能力 | 位置 | 结论 |
|---|---|---|
| standard preset delegation 组（`subagent` spawn，continuable） | `dsh-web-app/presets/standard.patch.yml` | **主路径**。与 cabinet"全新委派+内嵌原文"不变量天然同构；`modelSelectionSettings: true` 已启用，支持按委派下发 provider/model/reasoning_effort |
| 实验性 agent-team（`spawn_teammate`/`send_message`/`team_task_*` + 共享任务板） | `@deepseek-ai/dsh-experimental-agent-team-profile` | **不作主路径，借三点**（见下） |
| skill-filesystem + tool-skill | standard preset 已挂载 | 用 `ctx.skills.register` 内嵌注册 4 个技能，`/cabinet` 手势可用 |
| `list_subagent_models` | dsh-tool-subagent | 钉扎路由可用性核对手段，写进议事计划第 0 步 |
| cordis patch + HMR | dsh-app-boot | 阁员钉扎表做成插件 config，改 profile patch 即热生效——**比 PI 侧"改文件+重载宿主"更好** |

**agent-team 的三点借鉴**（修正早期"不值得借鉴"的粗糙判断）：

1. **`send_message` 续谈语义**——cabinet README 自述"宿主若支持跨回合 resume，可优化为续谈省 token"。dsh 的 continuable subagent + send_message 就是这个能力，列为 **v0.2 优化项**（v0.1 保持与 PI 版行为对齐，不用）。
2. **`wait_agent` 的 `noProgress` 语义**——"无人在跑立即返回、先唤醒再等待、等后重读状态"，比 PI 的"超时→续等→缺员"更精确。（v0.1.2 修正：该工具仅在实验性 agent-team 包内，standard preset 未挂载——语义留作记录，v0.1 落地文本已改用"完成通知 + list_agents 核对"。）
3. **Lead 权威 domain 层强制**的架构思想——提示我们：内阁纪律中可固化为代码的部分（如预算门），dsh 侧可经 `tools/pre-execute` 钩子做硬执法，方向性借鉴，不进 v0.1。

**明确不采纳**：`team_task_*` 共享任务板与成员互发消息——内阁核心不变量是"阁员不直接通信、父智能体是唯一集成点"，team 恰恰允许成员互发，逆机制打补丁不可取；且该包自述 experimental、无稳定性承诺。

## 四、dsh-cabinet 设计（v0.1 落地件）

### 4.1 结构

```
dsh-cabinet/
├── package.json            # dsh.bundle.patch 声明；无 dsh peer、无运行时依赖
├── cordis.patch.yml        # insert 一行 dsh-cabinet + 八席钉扎表（config.ministers）
├── lib/index.js            # apply(ctx, config)：注册 4 技能 + cabinet_start 工具；纯函数导出
├── ministers/              # 8 件阁员定义（从安装包逐字搬运，frontmatter 保留作档案）
├── skills/                 # cabinet.md + roles/{coding,writing,research}.md（dsh 工具面适配）
├── config/tiers.json       # 档位预算唯一真源（原样）
├── schemas/protocol-v2.json# 议定书字段真源（原样）
├── verify.mjs              # 发布门 35 项
├── smoke.mjs               # 41 项纯函数/加载器测试
└── README.md
```

### 4.2 映射关系

| PI 侧机制 | dsh 侧对应 |
|---|---|
| `plugin_local_cabinet_start` 工具 | `cabinet_start`（raw `ctx.tools.register`，原生 JSON Schema） |
| manifest contributes.skills ×4 | `ctx.skills.register` ×4（cabinet / cabinet-roles-coding / cabinet-roles-writing / cabinet-roles-research；frontmatter name 改为 dsh 合法 kebab-case） |
| 全局子智能体目录的阁员定义 | `ministers/` 人格文本（`cabinet_start` 生成计划时剥 frontmatter 逐字内嵌）+ config 钉扎表 |
| frontmatter `model:`/`thinkingLevel:` | 钉扎表 `{provider, model, reasoningEffort}`，委派时以 subagent 参数下发 |
| 阁员模型调节面板（views + onPanelInvoke） | **取消**——改 profile `cordis.patch.yml` 的 `id: dsh-cabinet` config（整体替换语义，八席列全），HMR 热生效；授权/导出/两轨同步/指纹脏标整个问题域消失 |
| Task / TaskWait / TaskList | `subagent`(run_in_background 并发) / 完成通知 + `list_agents`（v0.1.2 修正：无 wait_agent） |
| Plan 模式宿主禁用插件工具 | 保留对应提示（Plan 模式工具受限时停开） |
| 发布门 verify.mjs / smoke.mjs | 同名保留，断言面向 dsh 结构重写（TIERS==tiers.json 逐字段机检、patch 幽灵键检查、PI 工具名残留零容忍等 35 项） |

### 4.4 不变量保持

- 编排计划自包含（人格+钉扎内嵌，父智能体读完即可执行全场）；插件运行期无 I/O、无状态（文件读取仅在加载时）。

## 八、已知边界与遗留项

- 预算硬顶/cites/字数校验为计划文本规则，父智能体自律执行（与 PI M1′ 一致）；v0.1.1 已把红队铁律从自律升级为"失败关闭判据 + 响亮中止"，其余纪律的机器回读（归档审计器：events 对账 cost.calls）列 v0.2。
- 版本闸（v0.1.1 已补）：peer 钉 `^0.2.0-rc.2`（会咬人的范围；`workspace:*` 系列被闸门翻译为宿主版本、永不拒装，不可用）+ apply() 加载时 API 形状探针 + package.json 记录已验证宿主版本号。
- 钉扎路由可用性依赖运行时核对；Settings → 子智能体白名单未启用时委派参数可能被拒，计划已内置回退+披露路径（红队例外见上）。
- token 参考轨量测：dsh token-meter 是否暴露子智能体用量待实跑确认。
- v0.2 候选：send_message 续谈替代冷启动；pre-execute 预算钩子（先实证宿主是否暴露派发拦截点）；人格改路径引用（前提：verify 加简报人格哈希==ministers 文件哈希机检）；故障注入测试（覆盖回退路径与空 sessionModel 两类静默故障）；每场记录"闸拦截次数"入 index.jsonl 使 ROI 可算。
- 发布门环境声明：node --check 与 smoke 经子进程执行，沙箱禁 spawn 环境（如 dsh 内跑 verify）记 WARN 不记 FAIL；"全绿"以普通 Node 环境为准。
